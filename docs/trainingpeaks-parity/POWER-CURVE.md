# Additive full power curve

The existing personal-statistics endpoint now adds a bounded `powerCurve` DTO from its already-fetched cycling power-curve bundle. The original eight `bestEfforts` cycling anchors, Home history, pace models and provider query count remain unchanged. There is no provider write or new account/database configuration.

The version1 DTO contains `sport:"Bike"`, `kind:"power"`, `unit:"watts"`, `source:"intervals-power-curve"`, exact `{oldest,newest}` window, `points` and nullable `warning`. Each point contains the exact supplied `duration_seconds`, nullable `value`, native `activity_id`, source date/name and `estimated:false`. Optional native W/kg and recording indices are included only when verified. The public schema's `watts_per_kg` curve has separate `wkg_activity_id` winners; W/kg is therefore attached only when that explicit winner matches the watt winner at the same duration. No weight division or synthetic conversion is performed by production projection.

The source seconds axis must be strictly increasing, unique positive safe integers, aligned with its values and any supplied optional arrays, and at most10,000 points. No arbitrary24-hour cutoff removes valid longer source curves; existing effort-detail selection retains its separately established bounds. The source period identity/bounds and point dates must match the requested window. Values require a valid native source identity and in-window metadata, reject explicit sport mismatch or ignored power, and cannot exceed a known whole recording duration. Missing, nonfinite or negative values remain null, while measured zero remains zero. Unknown attribution remains unknown. Invalid indices or a separately won W/kg sample are omitted and warned about.

## Proposed unfiltered All and native-sport demand reader

Read-only next-slice proposal, not an implemented replacement for the existing Home/personal-statistics contract. The current `personal()` deliberately reads cycling power and Run/Swim **distance pace**, projecting the legacy/full power DTO from Ride only. Reinterpreting its Run branch as power would break existing Home and pace consumers. Tagged Power now has genuine per-recording all-sport inputs, but selecting a tag must not be necessary to enable an unfiltered Run or All power chart.

The [official API schema](https://intervals.icu/api/v1/docs) exposes athlete power-curves with required native `type`, explicitly including Run and the other native enum values. Its description includes the native sport's matching types/family. It does not declare an All enum or establish omission as combined All behavior. Native type/filter serialization should not be guessed. A single-sport native aggregate Run read is therefore a documented future optimization, but a combined All request cannot honestly be implemented by sending type All or silently reusing Ride. The same official schema documents `GET /api/v1/activity/{id}/power-curve.json` as an individual recording's normal power curve when no fatigue selector is supplied. The prior private inventory includes genuine Run records declaring a watts stream; Run power is not merely a hypothetical enum. No new authenticated GET or populated Power wire probe was performed for this proposal.

The smallest consistent addition is a separate demand-only `GET /api/performance-curves?kind=power&sport=all|<native-selection>&start=YYYY-MM-DD&end=YYYY-MM-DD`, without tags, catalog scope or catalog membership. Empty tags normalizes to this unfiltered reader. Home, personal statistics, legacy eight anchors, old Bike full-power DTO and distance Pace remain unchanged. The new desktop adapter explicitly parses its separate source identity rather than treating the old Bike-only full curve as All.

Proposed response: version1, kind power, unit W, source `intervals-activity-power-curves`, unitPolicy `native-watts`, valuePolicy `native-reported`, tagsSupported false, exact `{sport,nativeTypes}` selection, exact `{oldest,newest}` window, full native duration points and explicit coverage. Point provenance binds the requested native recording ID/type/local date/name, with `estimated:false`; values are finite nonnegative native watts or null. Zero remains measured, wholly absent durations stay absent and no reference-anchor interpolation occurs. No sourceTags field or native tag catalog is required. Optional indices remain structural metadata; source actions open ordinary Summary unless separate raw segment evidence establishes an effort highlight.

All aggregates actual recognized native recording types in the date-bounded inventory, not a list of guessed aggregate All calls. Ride/Run/Swim selections retain their established families; other native selections are exact, and combined selections deduplicate physical recording identities before aggregation. Unknown native types or conflicting/invalid identities cannot silently become Other or measured winners. The normal per-record source parser can reuse the tested raw shape/alignment/provenance/ignore-parts validator from the tagged source without requiring any membership data.

The narrow inventory must include ID/type/date/name, known elapsed/moving duration, stream types, source sync revision, `icu_ignore_power` and relevant `ignore_parts.power`. Known absent watts streams and whole-record power ignores are excluded with separate counts. Missing stream availability permits a bounded native curve read rather than assuming no power. Unknown duration must remain unknown: it cannot become zero, while an otherwise valid native source sample may be retained with incomplete eligibility coverage; known-too-short samples are masked. Unknown stream/length metadata should have explicit counts and a partial warning rather than imply those checks passed. Missing/null/malformed tag membership has no effect on this **unfiltered** pool. Relevant ignored-part overlap or unavailable source index bounds must mask a candidate, while unrelated HR/pace flags do not suppress power.

At most128 deterministic eligible recordings per request, four reads at a time, supplies exact-duration maxima. Cap omissions remain `skippedForCap` and partial; they are not a claim about unfetched winners. Coverage should partition valid selected-sport inventory into eligible, known no-power and ignored sources, with fetched/skipped, failed/missing, unknown samples, unknown stream/length and invalid/conflicting inventory counters. Inventory at the10,000-row bound, incomplete metadata, failed/missing/ignored-part samples or cap omission remain explicit. All attempted sources failing returns502; a genuinely empty eligible set returns no points. Reuse account/actor-scoped source caches, independent caller cancellation, shared deadlines and provider-refresh invalidation, with no new reads triggered by Home or default tagged-catalog logic.

Minimum acceptance: unfiltered All includes a genuine Run winner over a slower Ride at one exact duration; Run/TrailRun and Ride families remain correct; All/combined deduplicate identities; absent/null tags neither exclude sources nor load a catalog; known no-power/ignored/short/partial-ignore and unknown stream/length states stay truthful; zero/null/gaps and optional indices preserve their meaning; the128 cap cannot claim complete coverage; malformed/cross-account/window responses and late canceled reads cannot replace a current snapshot. Tests must independently compare per-record raw power/time samples, prove no provider writes, and exercise actual source Summary dependencies. Existing Home/personal-statistics payloads and query counts need unchanged-contract regressions. This proposal adds no Power Profile normalization, W/kg categories or physiological equivalence claim. Implementation is intentionally held until the current native-tag browser artifact finishes.

Malformed full projection or unavailable Ride data returns `powerCurve:null` with a static `powerCurveError`; raw provider messages and private metadata are not exposed. The legacy anchors remain present when their preexisting contract still succeeds. A successful absent source period returns an empty points list. Missing exact durations are never interpolated or filled from nearby values.

The observed Peak Power grid's fifteen durations are5,10,12,20,30,60,120,300,360,600,720,1200,1800,3600 and5400seconds. Frontend code must use exact equality to select these samples from the full DTO, leaving an absent or null anchor unknown. The synthetic preview adds fifteen explicitly listed demonstration samples and binds known points to eligible in-range synthetic recordings; its legacy eight-anchor fixture remains unchanged. This demonstrates workflow behavior, not numerical identity with a live TrainingPeaks account.

Seven new independent backend tests cover exact samples, zero/null, provenance and period bounds, malformed/oversized/alignment rejection, optional index and W/kg ownership, unchanged legacy anchors/provider request count, account/window cache isolation, generic additive failure and synthetic preview contract. Existing performance-curve tests also remain required. Backend projection currently represents the existing cycling family; fourteen-sport and subtype-specific Peak Power equivalence is not established by this additive DTO. No complete dashboard or pixel-parity claim follows from it.

## Implemented separate unfiltered native-sport reader

After the native-tag browser gate, the proposal above was implemented as an additive demand-only reader. The earlier Bike-only statements describe the preserved personal-statistics projection, not a restriction of this new native source. `GET /api/performance-curves?kind=power&sport=all|<native CSV selection>&start=YYYY-MM-DD&end=YYYY-MM-DD` now returns `NativePowerCurveResult`, declared in `native-power-curve-model.d.mts`. A valid empty tags array is removed by the dispatch adapter and uses this reader, without a catalog or membership requirement; nonempty tags continue to use the existing separate version2 tagged service. Home, personal statistics, legacy eight-anchor queries and full Bike/Run/Swim distance-Pace payloads are unchanged.

The new version1 envelope is explicitly distinguished by source `intervals-activity-power-curves`, kind power, unit W, unitPolicy native-watts, valuePolicy native-reported and tagsSupported false. It binds exact selection/window and returns the full native seconds axis with nonnull recording ID/type/local date, bounded name, nullable watts and estimated false. There is no false global Bike label or sourceTags requirement. All uses actual recognized native records; Run/Ride/Swim keep their established families, and combined selections deduplicate by native identity. The normal per-record PowerCurve validator is reused as a pure shape/ignore/provenance function; it performs no tag/catalog access.

Coverage partitions `inventoryRecords = eligibleRecordings + excludedWithoutPower + excludedIgnoredRecordings` and `eligibleRecordings = fetchedRecordings + skippedForCap`. Failed/missing sources, invalid/conflicting inventory, masked samples, unknown stream availability, unknown recording length and cap omissions mark partial. `unknownLengthRecordings` and `unknownStreamRecordings` are overlapping subsets of eligible records. A native sample can remain known when its inventory length is unknown, with that incomplete check declared; known-short samples cannot win. Explicit no-watts streams and whole-record power ignores are excluded. Relevant ignored power parts mask overlapping or unverifiable index samples; unrelated HR/pace ignores and missing/null/malformed tags do not remove unfiltered power sources. A genuinely empty pool stays empty, and all attempted sources failing returns a safe502.

Requests are isolated by trusted actor/origin/provider account, exact window/selection and athlete-local day. Validated source caches also bind source date/type/length/sync/ignore metadata. Four source reads per batch and four active windows are bounded; caller cancellation does not cancel shared work. Each operation has a60second deadline. The existing limits are retained: at most128 fetched records,10,000 inventory rows/points per native curve,100,000 processed source points per window,100,000 retained source-cache points,10million retained window-cache JSON characters and5million response characters admitted incrementally before winner copies. Resource errors request a smaller range; exact data is not truncated. Cache/account/provider refresh invalidation is independent of the existing unfiltered/tagged readers.

Thirteen backend regressions exercise strict selection, All versus native families, Run/TrailRun winners over cycling, tag-independent membership, zero/null/full axes, incomplete metadata, ignore/short/provenance, dedup/conflict, real128-of130cap, raw duration-weighted power samples, scoped/coalesced caches/cancellation, safe failure cooldown, weighted/incremental resource limits, authenticated function routing and normalized empty tags. Actual localhost preview checks source Summary lookup/comments/personal/attachments/analysis/route, zero native writes, identical Home payload before/after native demand and zero native Power reads until explicitly requested. New source records also pass the unchanged strict UI workout validator with physical raw power. Populated live native per-record Power responses were not newly queried; official schema and deterministic native-shaped tests establish the implemented adapter contract, not measured TrainingPeaks algorithm equivalence. Integrated UI/browser verification remains a separate gate.
