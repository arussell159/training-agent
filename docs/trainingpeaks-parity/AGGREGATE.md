## Numerical and missing-input boundaries

Intervals.icu's daily CTL/ATL and selected load are real measurements/calculations from that provider. They are not proof of identical TrainingPeaks algorithms, historical thresholds, seed fitness, sport load factors or form-date conventions. Current app form is CTL minus ATL on the supplied day; whether the reference displays a prior-day balance must be observed. Preserve gaps; do not draw an invented continuous series across missing source days.

Official provider sources expose `power_load`, `hr_load`, `pace_load`, `hr_load_type`, and `pace_load_type`. These can support honest separate stress displays, but an HRSS value is not automatically TrainingPeaks hrTSS. The provider's [server-side data model](https://forum.intervals.icu/t/server-side-data-model-for-scripts/25781/16) distinguishes those fields and records zone durations in seconds; the [current OpenAPI schema](https://intervals.icu/api/v1/docs) was also checked directly. A separate [official forum discussion](https://forum.intervals.icu/t/hr-zones-for-weight-training-workout-and-yoga/107959) documents sport-specific CTL/ATL factors, another reason not to assume numerical equivalence from matching one activity.

Aggregate HR-zone times must carry the zone-boundary scheme used by each recording. Summing Z2 across changed thresholds without disclosure mixes different intensity definitions. Either use consistently configured equivalent test data or group/differentiate incompatible boundary signatures. Missing zone arrays are unavailable, not all-zero training.

## Implemented aggregate data slice

`intervals.mjs` now projects `power_load`, `hr_load`, `pace_load`, `hr_load_type`, `pace_load_type`, and validated `heart_rate_zones: { seconds, boundaries_bpm, threshold_bpm }` in workout summaries. Missing/malformed zone arrays become null; genuine zero measurements remain zero. Completed summaries read the actual recording, independently of a paired plan's fields. Compact workout rows retain canonical `provider_type` and completed `activity_type` for subtype/filtering. `intervals-history.mjs` explicitly requests the required public measurement fields for historical pages. Existing summary fields are preserved.

`ui/src/lib/aggregate-analysis.ts` exports `aggregateActivityHistory`, `aggregateMetricValue`, and typed daily/weekly periods. It deduplicates paired recordings, filters by recorded sport and inclusive athlete-local dates, clips partial weeks, and returns each metric as `{ value, observed, missing }`. All-missing totals are null; mixed coverage retains the observed sum and missing count; an empty period is zero activities with zero observed/missing measurements. It does not calculate a weekly IF or invent missing TSS.

The helper returns compatible HR-zone groups separated by canonical sport, historical boundaries and threshold, plus a count of recordings without usable zone data. It clones zone arrays rather than mutating source records. Separate load algorithms remain named by their provider source; no field is relabelled hrTSS/rTSS as an equivalence claim.

Browser training-payload types and validation now recognize these measurements. Two existing planned-value formatting calls were narrowed to numeric values so added metadata cannot enter a numeric field. Historical snapshots generated before this projection still require ordinary provider refresh/reconciliation to acquire new aggregate fields; unavailable data must remain visibly unavailable until then.

Native shapes were checked against the credential-free [current OpenAPI schema](https://intervals.icu/api/v1/docs) and the official [activity data-model explanation](https://forum.intervals.icu/t/server-side-data-model-for-scripts/25781/1). Power boundaries come from **`icu_power_zones`**, not athlete-settings `power_zones`; native durations are `icu_zone_times: [{id, secs}]`. Standard Z1…Zn entries are matched by ID, not position. The overlapping SS bucket is excluded from standard-zone totals; unknown/custom ID schemes become unavailable rather than guessed. Pace uses `pace_zone_times` or selected `gap_zone_times`. Boundaries are percentages and historical threshold values are retained; no current-account threshold fallback occurs.

Compact summary properties are `power_zone_times` / `pace_zone_times` with `{basis, unit, boundaries_percent, seconds, threshold}`. `basis` is `power`, `speed` or `gap-speed`; threshold is watts or metres/second respectively. Browser payload validation rejects malformed arrays or a mismatched basis. Paired completed summaries use only the actual source record. Existing compact snapshots need ordinary provider refresh to acquire new fields; old missing values remain unavailable. Historical source threshold correction stays in the separate `recorded-analysis-thresholds` module.

`aggregateActivityHistory` now also returns `maxima` and `missingZoneActivities` per period, compatible zone group `periods`, `powerZones`, `paceZones`, and missing counts. Zone periods are sparse measured buckets: consumers should join them to the returned complete day/week period inventory and show missing coverage explicitly. `aggregateFastestPace` converts only a measured positive maximum speed. `aggregateDailyMetrics` preserves exact saved projections, including deliberate null clears, over native fallback snapshots for the same date. Subjective labels never enter arithmetic. The latest exact projection for a date wins; all returned metric and zone arrays are cloned.
