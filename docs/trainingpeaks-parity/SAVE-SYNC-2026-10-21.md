# Save and background synchronization audit — 21 October 2026

The existing synchronous editor save waits for a provider read, provider write,
provider verification read, then database snapshot/projection/cache work. Creation
additionally checks for an existing external identity. Navigation could therefore
wait for multiple 30-second provider deadlines. The previous durable mutation
queue covers only moves and descriptions; direct editor writes use durable claims
but acceptance still depends on the external provider.

## New acceptance boundary

`POST /api/workout-commits` accepts a stable operation identity and workout revision.
One compare-and-swap update of the existing encrypted backend `app_settings` record
commits **both the complete app input and its pending operation**. Acceptance does
not perform an Intervals.icu request. An acknowledged response means a backend
database transaction, not an optimistic cache update or an unawaited promise.
The separate browser outbox can report its own local transaction before handoff;
that must not be labeled backend acceptance.

New workouts retain `app:UUID` identities across mapping to `event:ID`; imported
workouts retain their original event IDs. `app:N` revisions require a matching
prior revision. Reusing an operation ID for different input fails. Fields include
full structured models, notes, descriptions, manual values, comments, personal
fields and pending repeat schedules. Personal attachments use the existing
draft-to-saved migration when `personalId` identifies the original draft.

`GET /api/workout-commits` returns accepted models and exact synced revisions.
`GET /api/workout-commits/{encodedId}/editor` restores a complete editable model.
Cached training-zone settings are loaded separately; absence produces the existing
zone error, rather than fabricated zone boundaries. A retry endpoint releases
actionable failed jobs; it does not bypass external revision conflicts.

## Worker guarantees and limits

Durable per-workout claims use database CAS; independent workers cannot claim the
same active operation. Four independent lanes prevent one slow workout blocking
all others. Queued obsolete edits coalesce, while creates and in-flight work retain
dependencies. A response acknowledges only its own revision. The latest accepted
model remains intact when an older job completes.

Existing/imported workouts use the existing GET/revision-guarded PUT/GET verified
adapter and durable direct-write claim. Deletions read back a 404. Unknown outcomes
are read back before repeating work. New app-owned creates use the officially
documented `POST /athlete/0/events/bulk?upsert=true` with a stable `external_id`.
The official guide explicitly scopes external-ID matching to the creating
application. Imported event identities/external IDs are never replaced.

Transient errors retain jobs with exponential backoff (capped at five minutes),
jitter and Retry-After support. Permission, validation, missing-record and revision
conflicts become actionable failures. Personal-field and repeat-schedule work
must complete before the entire accepted revision is marked synced.

Every minute, bounded read-only reconciliation checks up to eight synchronized
workouts per drain. Genuine external changes/deletions retain the accepted app
model **and** the external version, expose `externalConflict`, and report a failed
status requiring review. Provider snapshots cannot authoritatively overwrite a
pending app revision. Synchronized projection does not indefinitely override later
provider changes or deletion.

Conflict review and explicit resolution use GET/POST
`/api/workout-commits/{encodedId}/conflict`. Review stores a particular native
candidate and the current app revision. Resolution reads the provider again and
requires both that exact candidate hash and the unchanged app revision. Choosing
the app version queues a guarded revision; choosing the provider version adopts
the exact supported prescription without writing it back externally. Private
metadata/repeat work still completes independently before reporting its full
revision synced. Both complete versions and prior pending jobs remain encrypted
in `resolutionHistory`; capacity exhaustion rejects resolution without pruning
copies. An unknown resolution response retries the same operation identity.
Unsupported provider prescriptions cannot be adopted as partial editable models.
An externally deleted workout can be accepted as deleted; keeping a live local
prescription requires a separate new copy instead of resurrecting the old event.
The main audit records the corresponding comparison UI verification.

The standalone Node server wakes the durable worker every 30 seconds, independently
of browser tabs. Hosted request handling uses `waitUntil` for the initial attempt;
this is bounded by the deployed invocation's five-minute lifetime and is **not**
the independent retry scheduler. `/api/internal/workout-commits/drain` requires
`Authorization: Bearer <CRON_SECRET>` before app authentication. A configured
external/Vercel scheduler must call it for indefinite closed-browser hosted retries.
Without that configuration, later requests resume work, but indefinite retries
while the browser is closed are not guaranteed. No scheduler deployment was
performed by this backend subtask.

The encrypted ledger currently rejects acceptance above 2 MiB; it does not falsely
acknowledge a save when full. Completed job payloads are compacted while operation
hashes and the latest accepted model remain. Long-term archival is an explicit
capacity limitation, not an unlimited retention guarantee.

## Controlled verification

The new durability suite passes 24 tests: all three sport models; independent
acceptance with zero provider requests; delayed writes with rapid revisions;
older acknowledgments; restart recovery; uncertain create success; rate limiting;
expired credentials; two-worker ownership; duplicate clicks; create/edit/delete;
external conflict; acceptance failure; personal/repeat sidecar recovery; and later
external edits/deletions, tombstone projection, imported deletion guards, failed
create dependencies, empty start times, and explicit conflict-resolution races,
idempotency, unsupported candidates, deleted candidates and private metadata.
The final full backend gate passes 967/967, including definite 400 classification
for invalid form inputs, retryable storage failure classification, and valid
comments accepted before external creation. Five focused client recovery cases
also pass, covering persistent conflict decisions, exact replay after a lost
response and module restart, ordinary-save/choice coordination, rate limiting,
fresh external observations, and rejected imported handoff recovery. The first sandboxed full run could not connect its
localhost HTTP tests; the approved network-enabled rerun passed.

## Real configured integration

The app's existing stored provider athlete was independently checked against its
saved app snapshot and matched. A separate encrypted audit ledger used the same
production CAS implementation without draining unrelated accepted user work.
Swim, Ride and Run each completed create → durable acceptance → worker → independent
raw Intervals.icu readback → fresh-service exact model reopen → further edit →
worker → independent readback with the same event ID → second exact model reopen.
All three task-owned events were deleted after checking their exact unique
external ID and run identifier; independent reads confirmed 404 for each.

The three real backend acceptance samples were 513, 290 and 439 ms. This is a
small sample, not a percentile, and two exceed the 300 ms backend target. The
combined create-and-edit round trips were 10578, 11783 and 12007 ms, including
both worker passes, external reads and app reopens. The first sync was not timed
separately in this run; the reusable script now measures that boundary separately.
These Node/API results do not measure browser interaction or visual parity.
See [the raw evidence](LIVE-COMMIT-ROUNDTRIP-2026-10-21.json) and
`tools/workout-commit-roundtrip.mjs`. The worker scheduler and closed-tab hosted
execution still require deployment verification.
