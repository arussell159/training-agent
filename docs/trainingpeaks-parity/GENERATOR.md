# Workout Generator checkpoint

The lead observed the reference generator opening an unsaved structured builder after generation. This implementation preserves that boundary: **generation has no calendar/provider mutation capability**. The existing editor Save action separately performs the actual verified save. No real external generation requests or provider writes were performed during this worker's tests.

Authenticated `POST /api/workouts/generate` accepts exactly:

```json
{"date":"2026-10-22","sport":"Ride","intensity":"percentOfFtp","length":"duration","target":"range","prompt":"Five minute warmup, 3 x 2min work/1min recovery, five minute cooldown."}
```

Optional `variant` is `brick`, `day-off`, or `custom` and requires native sport `Other`. Supported canonical sports use the existing shared model catalog. Date is an exact athlete-local calendar day. Prompt must be nonblank and at most 1,000 characters. Length is `duration` or `distance`; target shape is `range` or `target`. Intensity options are `percentOfFtp`, `percentOfMaxHr`, `percentOfThresholdHr`, `percentOfThresholdPace`, and `RPE`. No client-supplied model name, credentials, calendar identity, tools or API configuration is accepted.

Success is `{model, warnings: [], generated: true, saved: false}`. No workout ID or refreshed calendar context is returned. `WorkoutGeneratorInput`, `WorkoutGeneratorResult`, option catalogs, `validateWorkoutGeneratorInput` and `isWorkoutGeneratorResult(value, attemptedInput)` are shared from `workout-generator-model.mjs` and its declaration. The result guard checks canonical date/sport/variant identity, a valid nonempty structured model, explicit unsaved markers and allowed result keys. The browser must retain pending input while generating, abort when cancelled, and open the result as an editable new builder draft. It must never silently retry generation or save automatically.

The service reuses existing `coachConfig()` OpenAI model/key configuration and the existing Responses HTTP transport, including abortable rate-limit retries and redirect rejection. It does not require GitHub or athlete/calendar reads. It requests [strict structured output through Responses `text.format`](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), disables response storage, and sends only the validated request plus the workout-only instructions/schema. It supplies no tools. Server code constructs canonical model identity and unique node IDs from a bounded step/repeat DTO, then applies the existing model validator. The model cannot choose the sport, private variant, date or end-condition/intensity unit system. Duration is whole seconds, distance physical metres (converted into the existing canonical Swim yard convention where applicable). Percentage bounds and requested target/range shape are checked independently. No FTP/HR/pace threshold is invented.

Bounds include 40 segments, 100 unique steps, 1,000 executed steps, 100 repetitions per group, 9,000 output tokens, 200,000 response bytes, and bounded human instruction fields. Refusals, incomplete responses, wrong shapes, invalid ranges, empty plans, excessive structures, code fences and machine-description envelopes fail safely. Only one assistant `output_text` JSON object is parsed; reasoning items, raw provider errors and API envelopes never enter model notes or descriptions. API credentials exist only in authorization headers. Error text is owned by the application rather than copied from provider bodies.

Generation has a 75-second server deadline and a two-request process concurrency bound; the caller may cancel earlier. The server route aborts on response disconnect and clears listeners in all outcomes. The browser's deadline should exceed this deadline (currently 90 seconds). HTTP/error codes include `GENERATOR_INVALID_INPUT` (400), `GENERATOR_NOT_CONFIGURED` (503), `GENERATOR_BUSY` (429), `GENERATOR_REFUSED` (422), `GENERATOR_TIMEOUT` (504), `GENERATOR_CANCELLED` (499), and bounded invalid/incomplete/unavailable output errors (502).

## Numeric RPE follow-up

The lead confirmed real numeric RPE targets in the reference builder: graph ticks 0/3/5/8/10, editable Range defaults 1–8 and text `1-8 RPE`. Input experiments established whole numbers 1–10 (blur rounds/clamps). The canonical model now retains typed numeric RPE and generation accepts numeric low/high bounds in that scale. RPE generation returns a concrete native-provider limitation warning; no physiological conversion or computed TSS is invented. The original temporary `GENERATOR_UNSUPPORTED_INTENSITY` checkpoint has been removed. See [numeric RPE preservation and limits](RPE.md) for native cue verification, exact private metadata and unsupported device formats. Numeric builder/graph UI integration remains a separate lead-owned acceptance gate.

The isolated calendar preview uses a clearly synthetic mocked Responses transport through the real generator validation/construction path. It returns a 19-minute warmup/repeat/cooldown fixture for browser workflow checks and leaves its provider records/writes byte-for-byte unchanged. It never loads real keys or calls an external generation service. Production has no synthetic fallback.

Initial verification: **701 backend tests passed**, including six generator suites covering configured transport and schema, the exact 19-minute repeat, selected units and canonical variants, invalid options/config with no transport, refusal/malformed/oversized output, timeout/cancel/concurrency release, no reasoning/response leakage, and no provider mutation in preview. Evidence: `artifacts/backend-parity-generator-tests.log`. The subsequent RPE test evidence is recorded in RPE.md. Source syntax and backend formatting pass. Browser behavior and final integrated build remain with the lead agent; no parity percentage is asserted here.
