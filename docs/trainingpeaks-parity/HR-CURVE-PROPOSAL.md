# Native HR curve selection contract

Read-only investigation after the773-test checkpoint. No production service, route or fixture changes are part of this proposal. The [official current schema](https://intervals.icu/api/v1/docs) lists actual native sport values for the optional athlete `hr-curves` query parameter `type`; it contains no `All` or `all` sport token. `curves=all` specifies the all-time date period, not combined sports.

A bounded authenticated probe used the application's existing trusted configuration, made exactly five provider GET requests and changed no training data/configuration: the same28-day HR curve with type omitted, Ride, Run and Swim, plus a matching narrow activity inventory. Every request returned200. Raw responses, recording identities, selected dates and joined evidence remain in ignored private artifacts.

The omitted-type response contained173 exact duration samples. Joining every winning identity to the inventory resolved163 Run winners and10 Ride winners; no winning recording had `icu_ignore_hr:true`. The Ride-only response differed at163 of173 shared durations, establishing that omission is genuinely combined rather than a default Ride curve. At all173 comparable duration points, omitted-type values exactly matched the highest returned Ride/Run/Swim sample. The uncapped inventory contained36 records across nine native types. These observations establish combined behavior for the measured families, not independent proof of every other native sport's inclusion or of tag-filter semantics; other sports may simply have no winning samples.

The smallest grounded app interface is a separate on-demand authenticated `GET /api/performance-curves?kind=heartRate&sport=all|<native-type>&start=YYYY-MM-DD&end=YYYY-MM-DD`. `sport=all` is an **app** selection that omits upstream `type`; a single supported native selection passes its actual enum value. Do not pass the app's all token upstream. Explicit multi-selection, private presentation variants and tags must not silently map to unfiltered data; they need a separately verified mapping/filter contract or a clear unavailable state.

An additive version1 response should bind exact selection/window, `kind:"heartRate"`, `unit:"bpm"`, `source:"intervals-hr-curve"`, exact sorted duration/value points and winning native identity/type/date. Preserve nullable missing samples, source-native numerical precision and actual zero distinctly. Validate native IDs, activity dates, selected sport membership, `icu_ignore_hr`, known recording length, array alignment and source date-token identity. Compact curve metadata in the observed response omitted sport, so exact inventory joins are required for native winner-type provenance. Missing inventory, caps, failed reads and unknown attribution need explicit coverage limits; native aggregate membership is not an independent proof of complete fourteen-sport coverage. Curve values must not be forced monotonically downward: the maintainer explains valid higher long-duration averages in [HR Curves question](https://forum.intervals.icu/t/hr-curves-question/38211).

The existing personal-statistics inventory is insufficient as an authoritative HR eligibility inventory: it omits `icu_ignore_hr`, coerces missing native types to Other and has no complete-coverage contract. Reuse its network cache only where the original raw fields and coverage genuinely satisfy the new contract. Prefer a separate bounded on-demand cache keyed by trusted account, sensor kind, exact selection and window; avoid adding HR network work to every existing Power/Pace request. Preserve safe failure cooldown, singleflight and clone isolation.

If genuinely audited combined coverage is required beyond the native aggregate, obtain a bounded complete recording inventory and derive actual native types rather than assuming Run/Ride/Swim. The documented bulk `activity-hr-curves.json` endpoint returns exact requested `secs` with per-recording `bpm` arrays. Validate each recording against inventory, deduplicate overlapping sport-family responses by native identity, and select the maximum only at exactly matching durations. Unknown/truncated inventory, omitted eligible rows, failed type requests or missing exact samples must keep coverage partial. The bulk response supplies no segment indices; source highlighting requires a separate independently matched raw recording/curve, without guessed bounds. The maintainer confirms this bulk API in [API access, post394](https://forum.intervals.icu/t/api-access-to-intervals-icu/609/394).

Before implementation approval, settle the selection/coverage DTO and independently test omitted-type combined requests versus single-type calls, mismatched sport/date identities, ignored/known-short recordings, missing versus zero, sparse axes, partial failures, account/window isolation and source readback. UI/browser verification must use independent raw-source segment evidence where highlights are shown. No numerical equivalence with TrainingPeaks follows from native endpoint availability.
