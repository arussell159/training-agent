# Remaining native peak and nutrition inputs

Read-only capability audit, October20,2026. The [current official OpenAPI](https://intervals.icu/api/v1/docs) was checked alongside the locally archived public schema. No authenticated athlete requests or provider/configuration writes were made. This is an API feasibility record, not a numerical or visual parity claim.

| Chart | Actual native contract | Additional work and limits |
| --- | --- | --- |
| Peak HR | Athlete `GET /api/v1/athlete/{id}/hr-curves.json` supplies duration-based `HRCurve` samples and winning activity identities. Bulk `activity-hr-curves.json` accepts explicit `secs` and a recording date range. | Add a separate cached HR request and validated DTO. Check `icu_ignore_hr`, exact duration/date/sport, known recording length, indices and incomplete coverage. Workout maximum HR cannot substitute for a sustained sample. |
| Peak Cadence | Per-recording `GET /api/v1/activity/{id}/power-curves.json?types=cadence` can request a curve for a recorded stream. | Requires eligible recording inventory and per-activity reads; no documented athlete-wide cadence endpoint or stream selector exists on athlete `power-curves`. Preserve native cadence units; do not silently double running cadence or equate swim strokes and cycling RPM. |
| Peak Speed; duration-based Peak Pace | The same per-recording stream-curve endpoint can request the velocity stream, e.g. `types=velocity_smooth`. | This is a candidate speed-duration source, not the existing distance/elapsed `pace-curves` contract. Need independently verified units/precision and duration semantics before production projection, plus recording inventory, ignored sensor/segment handling and bounded requests. A distance-curve point cannot simply become a duration anchor. |
| Power Profile | Power curves can include native W/kg, separate W/kg winners, ranks and fitted power-model information. | Existing cached samples can support a factual watts/Wkg view. Native rank cohorts, model type and reference profile population/normalization require explicit matching evidence. Intervals ranks, eFTP, CP/W′ or fitted models are not proven TrainingPeaks equivalents. |
| Macronutrients by Time Period | Native daily Wellness fields `carbohydrates`, `protein` and `fatTotal` store grams consumed. | Existing full wellness history retains them; implement bounded daily/range aggregation without new provider reads where history coverage is already loaded. Keep missing distinct from measured zero and report partial ranges. These are daily intake, not workout carbohydrate use/ingestion. |

The provider maintainer explicitly announced arbitrary-stream activity curve computation in [the March2025 release](https://forum.intervals.icu/t/intervals-icu-news-2025-03-14/93893/1) and demonstrates the source-comparison feature in [Compare activity power curves](https://forum.intervals.icu/t/compare-activity-power-curves/93705). The schema exposes `types` on the **per-activity** endpoint, not `field`, `fields` or `types` on athlete-level `power-curves`. Passing an invented selector to the existing cached athlete watts request would not establish cadence/speed data. Returned `stream_type`/`stream_name` must match the requested source. The generic `PowerCurve` schema uses integer sample values, so fractional speed precision needs verification rather than an assumed watts-to-speed reinterpretation.

The existing app caches Ride power plus Run/Swim distance-based pace bundles. It currently does not load HR aggregate curves or per-recording cadence/speed curves for these dashboard charts. `activity-bundle.mjs` can load complete recording streams for opened activities, but opening one recording is not coverage of an entire selected range. A local rolling-window algorithm over cached streams is an alternative only after specifying timestamp weighting, gaps, pauses, smoothing, ignored parts, minimum coverage and source units. Do not resample or fill absent streams silently; an instantaneous `max_speed`, `max_heartrate` or summary cadence is not a sustained best effort. Sparse native axes must remain sparse unless an exact requested native duration is independently returned. Effort-link indices still require raw-sample verification before highlighting.

For HR, date-token syntax/filter support follows the official athlete curve endpoints; bulk HR adds exact requested seconds and inclusive recording dates. New cache keys must include account, sport, sensor kind/stream, selected date window and requested axis. Failed sport/sensor reads should not erase healthy curves or generate values from stale fallback summaries. Candidate recording selection and winner provenance must independently reject mismatched/out-of-range/ignored sources, including `ignore_parts` when doing local calculations. No new native query was exercised in this audit.

The maintainer's [nutrition announcement](https://forum.intervals.icu/t/capture-carbs-protein-and-fat-intake/122594) establishes grams and daily intake semantics; historical custom nutrition fields are not automatically merged into native fields. In the app, `intervals.mjs` spreads native wellness rows into `wellness_history`, and `fast-context.mjs` retains their numeric properties. The existing 14-field Metrics entry editor is a separate observed workflow and does not yet offer these macro fields. Calories, exercise `carbs_used` and `carbs_ingested` cannot fill missing daily protein/fat/carbohydrate intake. The reference chart's exact totals/averages, grouping and empty-day rules still need observation before UI equivalence is claimed.
