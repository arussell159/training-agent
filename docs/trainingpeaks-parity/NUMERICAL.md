# Numerical comparison: evidence and remaining work

This is a read-only audit of one matched completed Run, not numerical parity certification. The lead agent observed TrainingPeaks and downloaded its original recording; this worker independently checked FIT integrity with the installed Garmin SDK, decoded only relevant measurements and read the matching Intervals.icu activity/settings through the connector. No recording, provider threshold, selected load method or source file was changed. Private identities, activity dates, filenames and raw details remain only in ignored `artifacts/trainingpeaks-parity/` evidence.

## What the numbers imply, without changing them

The timer-minus-moving difference is 2.655 seconds, about 0.165%. It cannot explain 36 versus 78.72. Intervals.icu's unavailable power threshold/load and available pace load, together with its priority setting, support pace-based selection. Its reported intensity with moving duration gives approximately 35.955, rounding to 36. A simple mean-speed/pace-threshold estimate is approximately 36.111. These consistency checks are not a reconstruction of its full graded-pace algorithm, and the integer `icu_training_load_data` value is not decoded as an undocumented model enum.

Using the published power relation `100 × hours × (NP / FTP)²`, device NP 272 W, current FTP 203 W and full FIT duration gives 80.224. Independently running the app's existing sample-range algorithm on original FIT samples gives NP 271.734 W and 80.067. Passing the same samples through the app's existing 1606-second compressed chart timeline gives NP 271.730 W and 79.933. None establishes the exact observed 78.72. The [official TSS formula](https://www.trainingpeaks.com/learn/articles/estimating-training-stress-score-tss/) defines the required power/threshold/duration relationship.

One diagnostic hypothesis deserves a controlled test: device NP/current FTP with the first 30 seconds removed gives 78.728, close to the observed score. This could reflect a rolling-window warmup convention, a different NP, threshold, time basis or rounding; this single case cannot distinguish them. No fixed 30-second subtraction or guessed historical threshold was implemented. TrainingPeaks also notes that changing the selected score source uses current threshold settings, making an attempted live recalculation an invalid read-only comparison. See [changing TSS source](https://help.trainingpeaks.com/hc/en-us/articles/115007309027-Can-I-change-TSS-to-Heart-Rate-Power-or-Pace).

## Existing architecture and concrete gaps

- `activity-bundle.mjs` already retains original FIT bytes and SHA-256, provider activity metadata, streams, FIT laps/swim lengths and generated views. General FIT session summaries, timer events and device threshold messages are not projected. The compact completed summary comes from `mapIntervalsWorkout`, whose duration is provider moving time, selected load is `icu_training_load`, IF is `icu_intensity/100` and NP is `icu_weighted_avg_watts`. Stream extrema are added; original session average power/work/NP are not substituted.
- `activity-analysis.mjs` builds its chart timeline from provider streams, caps sampling gaps to median cadence, then scales the entire timeline to provider moving time. `analysis-360.ts` computes sample-derived averages/work and 30-second power windows on that timeline. Recording, movement and timer time are therefore not independent first-class chart axes. This matters for pauses, dropouts, work integration, lap boundaries and peak durations; a single continuous short run is insufficient validation.
- The initial audit found that selected-range power IF/TSS used current sport settings rather than the completed activity's historical FTP. This could change historical selected-range results when current settings change. The follow-through below addresses that concrete source mismatch without changing the arithmetic.
- Historical report projection includes distinct Power/HR/Pace loads and their HR/pace model names. Follow-through now also projects activity `icu_ftp`, `threshold_pace` and power/pace zone snapshots. Recording-time and selected-model/override provenance remain incomplete. A generic `tss` field alone does not establish the originally selected model. Full provider activity retains more information than compact views.
- `zone_history` is a bounded history of settings observed during app sync, not a complete effective-dated threshold ledger. It does not establish historical running FTP. Current sport settings must not be substituted as historical truth. Intervals.icu's author explicitly distinguishes [activity FTP from current sport settings](https://forum.intervals.icu/t/custom-interval-fields/25942/31); the [public schema](https://intervals.icu/api/v1/docs) exposes activity `icu_ftp`, `threshold_pace`, LTHR, duration variants and model fields.

## Required next step and acceptance blockers

1. Prove recording identity: compare the two original files' bytes or canonical decoded session/sample channels, not date/title matching alone. Preserve unmodified private evidence and integrity results. Capture TrainingPeaks' selected score method, exact calculated NP/IF, calculation duration and applied sport-specific threshold; current settings, FIT device settings and a rounded calendar score are insufficient.
2. Add source-preserving projections before changing arithmetic: retain distinct native moving/recording/elapsed and FIT timer/elapsed durations, native selected load/model, original summary measurements and verified historical thresholds. Keep provider totals intact; label unavailable sources and conflicting provenance. Version/reconcile archived views deliberately so existing cached bundles do not silently keep old numerical contracts.
3. Validate matched continuous steady power, variable power, manual/auto pauses, recording gaps, sparse/smart recording, zero-power/coasting, short efforts near the 30-second window, and multi-session files. Add power-, pace- and HR-selected running cases, cycling and swimming; include historical threshold changes and identical source files under differing current settings.
4. Compare unrounded measurements separately from display formatting. Establish duration/zone/NP/IF/load/peak tolerances and calculate results per metric and case. Verify that local range selection, laps, charts, summary and aggregates use the declared time/model basis consistently.

The present blocker is a combination of different available thresholds/load models, incomplete historical provenance and unverified time/preprocessing conventions. The evidence does not justify hardcoding the reference score, modifying real thresholds, relabelling HRSS as hrTSS, or asserting numerical parity. The bounded investigation itself made no source change. Diagnostic output is in ignored `numerical-run-diagnostic.json` and `numerical-provider-context.json`; the original sanitized FIT summary remains in `reference-run-fit-summary.json`.

## Implemented historical-threshold correction

Both recorded analysis surfaces now take selected-range power IF/TSS thresholds from an explicit `recorded_thresholds` snapshot projected from the completed provider activity. Zone views use that activity's percentage boundaries and pace/power threshold. Current athlete settings, a planned workout's threshold, device FIT zones and an inferred NP/IF ratio are not substituted. Missing or malformed historical values remain unavailable.

The provider's completed/paired summary and lightweight history projection carry the snapshot with source/version. Older archived summary views upgrade from the already archived activity; they do not fetch or apply current settings. The client summary request schema changes from2 to3 so the HTTP/device cache can fetch the revised response. Original source totals and arithmetic are preserved.

Four focused backend cases cover independent planned/current/historical thresholds, missing/invalid fields, percentage boundary validation and old-summary upgrade. An additional UI numerical case uses a constant200W recording with an activity threshold200W while current settings differ; range IF stays1 and no historical threshold yields unavailable IF/TSS. A two-state synthetic browser runner, `tools/trainingpeaks-historical-thresholds-check.mjs`, checks positive historical FTP and missing FTP against deliberately unrelated summary IF/current settings. Its browser result remains pending the next integrated build. These tests establish source handling, not TrainingPeaks numerical equivalence.
