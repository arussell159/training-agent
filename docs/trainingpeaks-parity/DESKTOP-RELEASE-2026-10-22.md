# Desktop Calendar release evidence — 22 October 2026

The desktop Calendar appearance described here was subsequently rolled back at the user's request: the original sidebar, document scrolling, cards, toolbar and add-workout chooser are restored. Sync compatibility, draft recovery, hover request savings and earlier mobile fixes remain. Percentage targets now display whole numbers in fields, labels and chart prescriptions while preserving imported values. The release results below are historical evidence for the original implementation, not a description of the current Calendar shell.

This release adds the Calendar-specific desktop workspace, durable native completed-workout editing and comments, and contained recovery for missing editor assets. Intervals.icu remains authoritative. Dashboard, Nutrition and the mobile navigation retain their existing shell.

This is evidence for the implemented workflows, **not a certificate of complete TrainingPeaks pixel or behavioral identity**. The remaining limits below supersede broad parity language in earlier release notes.

## Implementation and provider contracts

- Calendar owns its desktop scroll surface and scoped shell. Display settings and loaded-workout search stay local. Hovering cards no longer starts workout data requests; opening an actual editor reuses the shared read cache.
- Completed activity changes, manual completion and comments extend the existing encrypted mutation journal, leases, conflict handling and operation receipts. They do not introduce another queue or database schema.
- A manual completion uses `/athlete/0/activities/manual/bulk` with deterministic `external_id = training-agent:completion:<event-id>`. Native `Activity.paired_event_id` is verified. An Event reverse activity link is an app projection, not an invented native field.
- Actual distance uses native `icu_distance`, including overrides. Native activity descriptions contain actual prose; planned event descriptions retain their prescription and separate comment section. Activity comments use native activity messages.
- Comments retain stable IDs and dispatch markers. An uncertain POST response is reconciled against native messages before any further action; the code does not blindly repost. Legacy comments are preserved and migration/posting is deduplicated.
- Native capability checks prevent unsupported summary edits and retain recorded streams/laps/device history. Existing activity duration is read-only, including an existing app-created manual activity: native PUT and manual bulk upsert ignored duration changes during independent readback. Duration can be supplied for the initial manual completion. Distance, TSS, calories, elevation and appropriate RPE/feel/metadata changes use supported native fields. Source-restricted stubs fail closed.
- Actual-only edits retain the full planned model and values and keep a single paired card. Native description baselines do not overwrite dirty local drafts or accidentally substitute planned prose.
- The verified asset defect was incomplete Calendar shell prewarming of lazy editor roots and their stylesheet dependencies. The manifest now includes those roots. A missing editor stylesheet is repaired before retry, within a contained editor error surface. Recovery retains the parent draft, permits one explicit retry, and never starts an automatic reload loop. An explicit shell reload first persists recoverable drafts and can be vetoed when persistence is unsafe.
- No scheduled recovery job is configured. The previous standalone server recovery interval was removed; a later visit, explicit retry or authenticated incoming webhook resumes pending operations. Existing visibility-aware live notifications/fallback frequency is unchanged.

### Bounded native integration

Six bounded disposable native investigations were performed while establishing the API contract. Each read the connection settings once. All six removed only their own temporary event/activity records and independently verified absence afterward. No existing athlete workout was edited. The investigations exposed the canonical distance and duration limitations above; failed experiments are not hidden as successful synchronization.

The final successful check is `artifacts/desktop-completed-live-contract.json`, run ID `c21f1784-80a1-41cf-825b-57794963cbf1`: planned creation, paired manual completion, supported activity edit with independent native readback, and native comment with independent message readback all passed, followed by verified cleanup. That run made 22 provider reads and six provider writes, one direct Supabase settings read and zero direct Supabase writes. Its journal/metadata adapters were in-memory; it does not measure production CAS latency or persistence. Durable state and failure behavior are covered by the mocked journal suite separately.

The journal byte bound measures the aggregate JSON passed to the mocked journal adapter. It excludes encryption overhead and other existing lock/metadata adapters; it is not a claim of three total production Supabase requests. Existing real provider webhooks can perform normal background reconciliation after a disposable native change. Those indirect account requests were not instrumented, so six reads / zero writes must not be represented as total account usage. No Supabase load test, new cron, attachment expansion or schema migration was used.

## Explicit remaining differences

AR branding, the current icon set and destinations remain. TrainingPeaks social/assistant/notification surfaces are not implemented. Routes Library is visibly unavailable; search covers loaded workouts. Unsupported Intervals fields are not silently faked. Private notes and arbitrary attachments retain existing storage and are excluded under the agreed scope. Existing native duration edits remain read-only for the verified provider reason above.

A complete lossless matched-data screenshot matrix, one-pixel certification of every control, exhaustive hover/disabled/error animation timing, and every proprietary TrainingPeaks Analyze/builder interaction remain unverified. The evidence identifies the specific measured and tested workflows rather than asserting exact parity for the entire product.

Production release uses the existing [live site](https://training-agent-omega.vercel.app). Commit identity, CI/deployment readiness and a bounded production smoke result are recorded in the final delivery and local release evidence after deployment.
