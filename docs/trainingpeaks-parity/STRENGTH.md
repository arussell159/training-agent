# Strength prescription contract

This is a real, separately typed exercise prescription and persistence adapter. It does not claim the reference's 944-exercise library, exercise history, media, completed-set recording, or full Strength visual parity. Custom exercise titles and prescribed values are exact user data, not fabricated library entries.

## Shared model

`WorkoutModel.strength?: StrengthPrescription` lives on the workout, not on interval repeats. When present, the native sport must be `WeightTraining`, `steps` must be empty, and `unstructured`/presentation variants cannot be enabled. Existing interval-based WeightTraining and title-only freeform Strength remain compatible.

`app-backend/lib/workout-strength-model.mjs` and its declaration export:

- `StrengthPrescription = {version:1, blocks:StrengthBlock[]}`.
- Block fields: `id`, `kind` (`single`, `circuit`, `warmup`, `cooldown`, `superset`), `title`, `instructions`, `notes`, `timeSeconds:number|null`, `recordMode:'completion'`, and `exercises`.
- Exercise fields: `id`, `title`, `instructions`, `notes`, `parameters`, and `sets`.
- Parameter columns: `{id,kind,unit}`. Set rows: `{id,values:{[parameterId]:number|null}}`. Every row includes exactly its current columns. Null means blank/unknown; zero remains a real value where the parameter permits it.
- `strengthParameterFields` exposes Weight and Weight/side (lb/kg), Reps and Reps/side, Duration (seconds), Distance (m/km/ft/yd/miles), Height (in), RPE and RIR. Duplicate kinds remain separate columns with separate IDs; adding a parameter defaults to another Reps column.
- `validateStrengthPrescription`, `isStrengthPrescription`, `newStrengthExercise`, `newStrengthBlock`, `addStrengthParameter`, `setStrengthValue`, `copyStrengthPrescription`, `strengthTotals` and `strengthPrescriptionText` are shared browser/backend helpers.

Observed constraints: workout/exercise title128, instructions1000, notes1000, exercise sets1–15, three default Single Exercise sets. Fresh Circuit, Warm Up and Cool Down blocks have their matching title, time600seconds, and one exercise with one blank set. A fresh Superset has title Superset and two exercises with three sets each; its time remains null because the inspected form has no Time field. Converting an existing block is a kind change that retains its sets/time; no extra rounds are invented. The inspected Record combo offered only For Completion. Empty exercise titles may exist in drafts but block persistence. The top-level workout title is also required on Save.

The first set's edited parameter propagates to every row, including an existing lower-row override. Other row edits affect only that row. Helpers clone inputs. A duplicated prescription regenerates block/exercise/parameter/set IDs while retaining values and references to the new parameter IDs.

Resource guards are app constraints, not asserted TrainingPeaks limits: at most100 blocks,200 exercises,12 parameter columns per exercise and bounded finite values. Reps are nonnegative integers, RPE uses integer1–10, RIR nonnegative integers; clocks are bounded to24hours. Catalog min/max values supply the remaining explicit bounds.

## Totals and provider compatibility

Three sets of15reps at50lb produce45reps and2250lb volume. Compatible lb/kg subtotals remain separate and are never added as if they shared a unit. Missing or duplicate Reps, duplicate Weight, and per-side combinations without a verified calculation rule keep aggregate volume unknown. Duration, TSS and IF are never inferred from reps, RPE or load. Block time is preserved as its own prescription field, not assumed to be measured workout duration.

The existing authenticated workout editor POST/PUT/GET routes own creation identity, revision conflict, read-only permission checks, independent readback and recovery. No new provider writes or routes are introduced by this model. Native sport is `WeightTraining`; the native description receives the full readable exercise/set/parameter prescription, including when the existing editor sends a separate manual Description. Identical workout instructions and Description appear once in native prose while retaining both exact private fields; a distinct introduction remains separate. Human text is parser-inert so native-looking instructions cannot become fabricated endurance intervals. There is no private JSON or `Workout editor v1` heading in the native description. The exact model uses the existing encrypted sidecar and commit gate.

Missing native parsed definitions are acceptable; unexpected native steps or positive parsed duration/distance/counts reject confirmation. Native projection preserves unknown planned totals and independently retains paired actual measurements. Manual planned fields remain supported through existing values. Native moves/renames refresh model identity on read; calendar copy preserves the private structure under its separate provider identity/date and later edits do not change the source.

A changed external readable Strength prescription retains a reviewable stored model and produces a blocking import issue rather than silently overwriting the external changes. The provider/private store still lack a cross-system atomic transaction or provider-side conditional PUT; the general transaction and credential-rotation limits in `RELEASE-REVIEW.md` apply.

The later missing-private-model guard and generic Description preservation are documented in `METADATA-ROTATION.md`. A reserved readable Strength prescription without its exact private model is review-only and cannot be reinterpreted as freeform. Editing or clearing a manual introduction preserves all exercise structure and workout instructions. These two added regressions bring the dedicated Strength tests to15 and the full backend checkpoint to760; complete credential migration remains open.

Text export includes title and readable prescription without metadata. FIT/ZWO/MRC/ERG reject this model because those adapters do not encode its exercise parameters. The returned provider warning states the native device/external-library limitation explicitly.

# Title-only Strength follow-up

The reference accepted a named Strength workout with no exercise blocks. Explicit `strength:{version:1,blocks:[]}` is now valid; incomplete nonempty blocks remain invalid. It creates and reopens in Strength mode with no interval steps or fabricated duration/load. Empty repetition/volume totals stay unknown. The readable native marker retains missing-private-model protection, while manual introductions can be edited or cleared independently. ## Observed Strength subtypes

The optional `StrengthPrescription.subtype` accepts exactly `Mobility`, `Functional Fitness`, `Yoga`, `Rock Climbing`, `Hybrid Strength` or `Stretching`. The browser-safe frozen `strengthSubtypes` catalog and `StrengthSubtype` declaration share those literals. Absence means ordinary Strength; selecting None deletes the property. Persisted null, blank, literal None, unknown labels, arbitrary objects and differently cased/spaced labels reject rather than normalize. Existing prescriptions remain valid without adding a default subtype.

Subtype is exact private editor metadata, preserved through the existing encrypted commit/readback model. Native sport always remains `WeightTraining`, including a Strength subtype named Yoga; it does not silently become a separate native Yoga activity. The human-readable native prescription and Text export include `Subtype: X` only when selected, without raw JSON/internal envelopes. This cue preserves meaning externally while documenting the provider's lack of equivalent TrainingPeaks Strength subtype semantics. It does not introduce an unsupported native sport enum or imply external filtering equivalence.

Three independent regressions add all-six/invalid-label checks, actual private create/reopen/revisioned change/explicit clearing, canceled-draft isolation, clean native prose, calendar copy, saved-library scheduling and subsequent edit independence, plus Text export. The targeted Strength suite now passes20 tests. Earlier counts above describe their recorded checkpoints; current full backend verification is recorded separately with the release gate. UI subtype popup/header and browser verification remain the lead's separate integration scope.

## Unset versus explicitly assigned start time

Optional private `strength.startTimeAssigned` is strictly boolean when present: true records an explicit time choice, false records explicit clearing, and an absent property preserves legacy unknown state without inventing a default. Null, strings, numbers, arrays/objects and an explicitly supplied undefined value reject. This marker is not a native provider field and never appears in readable descriptions or Text export. The actual native local date/time remains normal and independent; a nonzero native time is retained even when the marker is absent or false. The UI may distinguish empty from midnight using this private state without changing the authoritative native clock.

Both boolean states persist in the existing encrypted exact editor model through fresh create/read/revisioned save, calendar copy, library save and library scheduling. Changing a clone does not alter the source, other scheduled copies or the template. A definite denied update cannot publish a new marker merely because its native human-readable body is unchanged. Three additional regressions verify those lifecycle/privacy/validation guarantees, bringing the targeted Strength suite to23 passing tests. The lead owns the input display and integrated browser gate; no frontend or native API changes are part of this backend slice.
