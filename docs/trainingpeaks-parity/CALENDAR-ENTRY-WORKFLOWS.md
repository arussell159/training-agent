# Calendar entry workflows

The calendar chooser preserves AR branding/navigation and uses separate callbacks for Event, Metrics, Goals and Availability. These entries are not represented as workout sports. Note retains its existing native calendar-note flow.

## Event: desktop editor and saved summary

The desktop Event entry now opens a separate `DesktopEventDialog`, preserving the existing annual-plan/mobile `RaceDialog`. Name (maximum 150 characters), calendar date and Type are required. The native grouped picker includes all 29 selectable types observed in the reference, alongside its placeholder. Changing type preserves the typed name. Description is entered as plain text in an editable region; pasted markup is converted to text. A/B/C priority is optional on desktop, matching the observed unspecified reference choice.

Observed conditional Distance and ATP Event Type choices are retained for all 29 types. Running exposes its distance presets and three Run ATP choices; Cycling exposes five Bike choices; Triathlon and Duathlon each expose their three choices; the other observed types expose all fourteen ATP choices. Goal distance units follow the observed `mi`, `km`, `yds`, `m` order. Add Goals supports time, distance/unit, place, Finish Event, Set a PR and custom text goals. Save opens the persisted Event summary, including goals and Edit Event; calendar card reopening loads the same summary. A successful save is independently read back. Rejected saves retain the draft; ambiguous saves retain their original identity and expose recheck instead of silently creating another event.

The authenticated create/read/update endpoints use account/provider-scoped encrypted metadata for exact reference type, optional distance/ATP choice and goals. Intervals.icu receives the mapped native sport, native `RACE_A/B/C` category for prioritized races, name/date and **only human description text**. Its current official native Event schema does **not** allow plain `RACE`; the separate SharedEvent schema must not be confused with it. An unspecified-priority desktop Event therefore uses a neutral native `NOTE` plus private Event identity. It is rendered/reopened as an Event, protected from generic day-copy/delete and excluded from the generic Note editor. A private index preserves this identity when an older third-party/ATP race becomes unspecified without overwriting its external ID. Synthetic provider transport validates the official native category enum, and independent readback tests assert the neutral projection.

No editor or goal JSON is inserted into the provider description; goals do not invent workout duration/distance targets. Calendar date moves retain the metadata. Native description edits use the current provider prose while retaining compatible exact type/goals; incompatible native sport changes retain the private details but disable editing. Revisions protect metadata-only edits as well as provider edits. A/B/C events synchronize with the existing annual plan; unspecified priority remains a calendar Event without an invented annual-plan priority. Existing ATP endpoints still require their original A/B/C contract.

The creation identity remains unchanged across rejected and ambiguous requests. If that receipt identifies an Event changed since creation, the server returns `409 EVENT_REPLAY_CHANGED` with a validated existing Event identity. The editor keeps the draft and blocks creation retry, offers **Reload existing Event** to show authoritative current data, and retains the unsaved values behind **Review retained draft**. Reviewing and saving that draft uses a revisioned update of the existing Event, without another native creation. Malformed IDs and unrelated error codes cannot expose a recovery target. The client tests cover safe identity/error transport; the browser runner includes a lost-response/later-edit/recheck/reload/review workflow and must run on the corresponding integrated build before claiming verification.

Before a new Event request, its exact submitted fields, immutable identity and current draft are retained under the account/provider calendar scope. An ambiguous save survives Close/Cancel, reopening and a full browser reload; another Event entry resumes that pending save instead of creating a new identity. Incomplete retained edits and staged custom goal text are preserved separately from the immutable submitted request. Confirmed saves clear only their own record; a definite first-request rejection permits safe cancellation. A previously ambiguous request remains protected even if a later recheck is rejected. Corrupt/unreadable recovery records block another creation, and failed retention prevents sending a new request. Once the existing Event is loaded, **Discard retained draft** explicitly resolves the retained draft without changing the existing Event. These local recovery records are never inserted into provider descriptions. The pending-record unit tests cover isolation, malformed state, blocked storage and matching-identity cleanup; the expanded Event browser runner verifies the actual close/reload/reopen path on the next integrated build.

`tools/trainingpeaks-event-catalog-check.mjs` compares the actual captured conditional DOM catalogs against the implementation for every type, including ordered values/labels and distance visibility. Placeholder values are normalized from the reference `NONE_SELECTED` to the app's empty optional field value. The focused persistence tests verify Bike/Triathlon/Duathlon/general catalogs and yard-unit goals without generating native workout targets.

**Remaining reference limits:** exact rich-text formatting, other Event summary actions and lossless pixel geometry are not yet fully verified. ATP Event Type and goals are exact persisted metadata, not a claim to reproduce an unobserved proprietary planning calculation. `tools/trainingpeaks-event-check.mjs` covers the bounded desktop create/reject/save/summary/reload/edit workflow and all 29 conditional option sets on synthetic data; its browser run must use a build containing the catalog changes.

## Metrics: saved health entries and existing history

The Metrics chooser opens a real fourteen-field health editor for the selected day, retaining the existing actual history graphs and card/layout preferences. Values and per-field times are staged with Add before Save or Save & Close writes anything. Exact subjective scales remain private metadata when the provider has a different native scale. Supported numeric metrics and explicit notes use narrow native wellness patches. Zero, null, dirty dismissal, duplicate saves, revision conflicts and lost-response recovery are covered by independent browser/native-record checks. Opening it never creates a calendar workout. See `METRICS-AUDIT.md` for the verified contract and ten-group final browser evidence.

Reference chart defaults, graph geometry and broader proprietary behavior remain unverified; these implemented health-entry checks do not establish a pixel percentage.

## Goals and Availability

Goals has a dated list with the observed title default/150-character limit, ordered goal rows, completion checkboxes, keyboard/pointer reorder handles, Add New Goal, removal and guarded Delete/Cancel/Save. Blank rows are discarded on save; an entirely blank list is rejected with useful inline guidance, matching the observed absence of an empty-list save. Availability has inclusive start/end dates, unavailable/limited modes, the twelve observed available-sport choices, exact reasons and plain-text description. Limited mode requires at least one available sport. Actual native event identity and encrypted metadata preserve checklist identity/order/completion and exact labels across reloads.

Availability spans render as narrow ribbons rather than workout cards. A working popover opens current details and supports Edit, Delete and Close. The reference's Copy/Cut Options menu remains an explicit open gap. Brick/Custom selections retain their exact local meaning and show a concrete warning that the native provider cannot restrict availability to those types. No equivalent native restriction is claimed. Both editors await verified CRUD results, retain errors/drafts, protect in-flight writes, require explicit dirty discard/reload, and recheck uncertain operations by the original UUID. Unknown/corrupt annotation metadata uses the authoritative entry GET/error path instead of opening a workout editor.

The new client/helper suite and isolated `tools/trainingpeaks-annotations-check.mjs` cover this slice. Its final browser result is recorded in the Goals/Availability audit after the coordinated integrated build. These desktop additions preserve existing workout/calendar behavior and AR chrome; mobile annotation entry and complete reference menu/visual parity remain unverified.

## Verification

`tools/trainingpeaks-calendar-actions-check.mjs` runs only against the isolated synthetic preview. It checks date propagation, empty Metrics without workout writes, persistent graph layout, required Event names, pending-save dismissal protection, rejected-save draft preservation, native race creation/readback, immediate calendar updates and reload persistence, plus Note compatibility. Its generated screenshots/results remain under ignored `artifacts/trainingpeaks-calendar-actions/`. A synthetic workflow pass establishes local behavior only, not reference visual or full feature parity.

On the October 20 build-3 production preview, all five browser check groups passed with zero page errors. The Event test deliberately held a request to verify disabled fields/Cancel and Escape protection, rejected it before any provider write, then saved the retained draft through the production race-creation adapter and verified the native category/date after reload. The Metrics test saved and reopened a real layout preference; it did not claim to save health values.

Chooser sport persistence is independently covered by `tools/trainingpeaks-sports-check.mjs`. Workout Generator and unsupported distinct workout kinds remain absent rather than exposing dummy controls.
