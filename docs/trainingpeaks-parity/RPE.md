# Numeric RPE: app preservation and provider limits

The lead observed reference RPE Target/Range inputs, default Active 10 minutes at Range 1–8, and graph ticks 0/3/5/8/10. Direct input tests established whole-number bounds 1–10: 0 and -1 blur to 1; 10.5 and 11 to 10; 6.5 to 7. The backend validates rather than silently clamps imported/API values. Reversed ranges are rejected, preserving the app's existing invalid-range protection even though the inspected reference temporarily permitted reversed values. Ramp semantics were not observed and are rejected.

Canonical targets are `{kind: "rpe", unit: "rpe", mode: "single", value}` or `{kind: "rpe", unit: "rpe", mode: "range", start, end}`. Values are ordered integers 1–10. Exact targets remain private canonical data, display as `1–8 RPE`, and normalize to the 0–10 chart axis. No RPE-to-power/HR/pace conversion, estimated distance, threshold or calculated TSS is introduced. Existing model duration/distance semantics remain unchanged; computed load is null for RPE prescriptions.

The current public provider schema and [official native workout syntax guide](https://forum.intervals.icu/t/workout-builder-syntax-quick-guide/123701) expose power, HR and pace targets. The [official RPE feature discussion](https://forum.intervals.icu/t/create-rpe-based-workouts/53399) still requests numeric RPE and describes a cue before duration as the available workaround. This implementation therefore does **not** claim native Intervals.icu numeric RPE target parity.

The approved non-lossy app adapter retains exact RPE in the existing encrypted account-scoped private editor model and includes literal numeric RPE in native step instructions, for example `- RPE 1-8 600s intensity=active`. It sends no invented physiological target and no model JSON. Provider parsing must preserve prescribed duration/distance, role, cadence/lap semantics and the exact RPE cue; adding a physiological target or dropping/changing the cue fails independent readback. A lost response can only reconcile the same existing creation, never create a second event. Bare native RPE cues import as explicit typed targets; invalid or conflicting cues fail validation. Existing read-only/source restrictions still apply.

`workoutProviderWarnings(model)` exports the concrete provider limitation for display before Save. Editor loads, verified saves/creates and generated drafts return that warning. The app's own RPE graph and exact numeric edits remain usable after private metadata restart. Source-side edits that replace a cue must be read from fresh native content rather than restoring an obsolete private prescription.

The installed official Garmin FIT SDK target enum has no numeric RPE target. This encoder therefore explicitly rejects numeric RPE FIT export. Cycling ZWO/MRC/ERG encoders reject it too. No open/HR/power target is substituted. Text export includes the title and complete numeric prescription, with private metadata removed. Provider/device delivery of the literal cue is distinct from a verified numeric device target and is not certified here.

Workout Generator now accepts numeric RPE low/high DTO values, builds the canonical typed target, rejects fractions/out-of-range/reversed values, and returns the same limitation warning. Its isolated preview uses an injected mock Responses transport and performs no provider writes. All generated models also pass the existing native-description length check before they are returned as drafts.

This backend slice does not implement the builder target selector or measured graph controls; that UI integration and paired browser evidence remain with the lead team. All backend provider/API calls used by tests are disposable doubles. No real account workouts, settings or device deliveries were changed.

Verification: **708 backend tests and 497 registered UI tests passed**, including seven dedicated RPE tests. TypeScript no-emit checking, backend formatting and affected-file whitespace checks passed. Logs: `artifacts/backend-parity-rpe-tests.log` and `artifacts/ui-parity-rpe-tests.log`. The tests independently check cue retention and rejection, physiological-target absence, exact restart/readback, invalid numeric bounds and conflicting native cues, one-create recovery, all unsupported device formats, clean Text, and real generator/preview construction without provider mutation. These checks do not certify the still-pending RPE builder UI or native device-target parity.
