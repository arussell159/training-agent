# Native recording-tag wire discovery

Read-only follow-up to `CHART-TAG-FILTERING-PROPOSAL.md`. Exactly two authorized authenticated Intervals.icu GETs were performed using existing trusted configuration: native `activity-tags` and the prior bounded recording date window with narrow `id,type,start_date_local,tags` fields. Both returned200. No provider/configuration write, integration change, new access, native filter request or product implementation occurred. Private bodies, recording identities and date bounds remain in ignored probe artifacts only.

The native recording-tag catalog returned an explicit empty array. The narrow inventory returned36 records, all with `tags` absent; it supplied no explicit null, empty-array or populated-array membership examples. There was consequently no real tagged recording in this verified catalog/window to inspect, so the optional third tagged-detail request was not made. The empty catalog establishes a successful empty catalog response for this account, rather than a loading failure. It does not establish nonempty tag string normalization, matching operator semantics or a native equivalent of the separate populated TrainingPeaks tag list.

The [current official API schema](https://intervals.icu/api/v1/docs) documents `GET /api/v1/athlete/{id}/activity-tags` as all strings applied to activities, and `Activity.tags` as a string array. Its activities `fields` parameter explicitly excludes null values. Thus absent projected membership is consistent with a null native field; it does not independently establish an explicit empty array or authorize treating all missing/corrupt membership as known untagged. The schema alone also leaves null-versus-unknown application policy unspecified. The conservative proposal remains: validate explicit arrays, distinguish known empty arrays from unavailable membership, and report partial membership coverage for filtered requests rather than broaden them.

No native activity-tag names were available to test case, Unicode, commas, duplicate behavior or exact nonempty membership against a full tagged detail. Those are unverified wire behaviors, not negative findings. A future implementation should preserve actual exact strings, never split CSV or union private app tags, library reconciliation tags, calendar tags or TrainingPeaks names into this native source. Account catalog/filter cache identity and exact request binding still matter when a later account or native catalog contains tags.

The official ActivityFilter schema exposes `field_id:tags`, `operator` and untyped `value`, but no native filter serialization/any-versus-all behavior was tested. Correct tagged HR/Power aggregation must recompute from genuine matching recording curves or independently verified provider filters; masking existing aggregate winners remains invalid. Cadence/velocity can apply verified local membership before their recording cap. The lead's separate reference UI observation is still required to settle reference multi-tag semantics. No additional query or implementation is implied by this evidence record.
