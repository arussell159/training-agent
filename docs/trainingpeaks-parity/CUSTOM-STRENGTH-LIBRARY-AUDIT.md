# Custom Strength exercise library checkpoint

This slice provides the user's own persisted exercise definitions through the authenticated `/api/strength-exercises` service. It does not supply, scrape or imitate a TrainingPeaks built-in exercise catalog or media library.

## Implemented behavior

- Create/Edit has required title (128 characters), optional None plus the twelve observed muscle groups, default Reps and Weight lb columns, Add Parameter with supported kind/unit selection, a validated HTTPS YouTube/Vimeo URL, and instructions (1000 characters). Preview Changes shows the actual staged definition, a truthful No Video state or user-supplied video link, Edit Exercise, Cancel and Save. No exercise or workout is written during preview.
- Saving an independent new definition inserts a Single block with three blank sets. Creating from an existing exercise picker replaces that exercise explicitly and retains its set count and matching parameter values, including zero and null. Saved definitions and prescribed instances have separate identities. New instances carry `libraryExerciseId`; duplicate/copy preserves that link while refreshing instance, set and column identities. All workout modifications still use the normal `onChange`/Undo path.
- The Library panel has actual custom catalog entries, query, Owner and Muscle Group filters, No Exercise Results, insertion and Preview/Edit/History/Delete actions. Catalog edits and deletion never rewrite existing workout prescriptions. Known legacy prescriptions are shown separately; they are not presented as prebuilt catalog data.
- Exact saved-exercise history uses the opaque `libraryExerciseId`, with same-name definitions kept separate. Returned history is explicitly retained-calendar prescription coverage; actual set results are unavailable. Legacy name matches are labeled separately and are not merged into exact-ID history. This is a known difference from the reference's completed exercise history.
- Authenticated account scope, catalog revision, row revision, editable/read-only state, full normalized definition and returned operation identity are checked before accepting success. New exercise IDs are server-owned opaque identities; the client never derives them from operation UUIDs or exercise names.

## Failure and recovery behavior

The complete immutable operation is durably stored under `strength-library-pending:<opaque accountScope>` and read back before any write request. If local storage is blocked/corrupt or cannot retain it, no new write is sent. Recovery storage has an explicit retry control. Busy guards prevent duplicate writes. Lost/invalid responses keep the same operation and definition; remount recovery only sends `reconcileOnly` with the original identity. Cancel/Close cannot discard an unresolved operation.

Only a known initial precommit validation/rejection, read-only rejection or revision conflict clears the unsent outcome for editable retry. A rejection during an already uncertain recheck retains the original intent. Another account cannot acknowledge or mutate that intent.

`REPLAY_CHANGED` is handled separately from a generic conflict. The client requires the exact operation ID, account scope and safe saved exercise ID as receipt proof, then independently reloads the current same-account catalog and that exact exercise. The changed definition is shown separately while the original draft is retained. Explicit Review retained draft acknowledges the resolved changed outcome and opens a new revisioned edit; it never overwrites automatically. A verified deleted outcome offers explicit keep-deletion or create-new-from-retained-draft choices, with a fresh operation only after the user chooses recreation. A failed catalog/row load or account change cannot clear recovery. A confirmed save whose workout insertion callback fails retains its confirmed result for insertion retry without another library request.
