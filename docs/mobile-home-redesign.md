# Mobile homepage layouts

The new mobile Home layout follows the hierarchy of the supplied Aman Birdi PureGym redesign: a personalized photo header with a translucent stats panel and horizontally scrolling session cards. The hero uses neutral white and gray surfaces to blend with the mobile safe area, with AR Performance's blue accents. The site header shares ATP's fading navbar blur, with content scrolling beneath it. It retains the existing workout, recovery, nutrition, race, and history data sources.

Five supplied Waco and Texas race photos are optimized as WebP assets. The header uses the Texas finish scene, session cards vary between cycling and running photos, and the race card uses the Waco cycling photo. Each photo includes subject bounds; `HomePhoto` fits those bounds into the card on resize, keeping the athlete's head, body, and bike in view. A blurred full-bleed layer of the same photo fills the remaining card area, and the source photo's outer margins blend into it without blank edges. The source JPGs remain untouched. The large decorative hero arrow has been removed.

The redesign applies below 768px. Desktop continues to use the original dashboard. Missing measurements remain unavailable, and the weekly session ring uses the athlete's time zone and actual scheduled/completed sessions.

The **Daily snapshot** section uses a two-column grid: HRV and RHR on the first row, Sleep and a compact Nutrition card on the second row. Sleep includes a duration trend over the same displayed recovery period, with a seven-day average and shaded range. Missing nights remain unavailable. Nutrition still opens the food diary and supports quick food entry.

The hero photo loads eagerly with high priority and asynchronous decoding. Session and race photo layers start loading within 200px of the viewport, so lower cards do not compete with the first screen. The same file supplies both layers and remains cached once loaded. Photo fitting and card dimensions remain unchanged.

Every photo wrapper aligns with its card bounds and inherits its corner radius. An explicit rounded clip contains the blurred background and fitted subject, including when mobile browsers composite those layers separately. Blur stays on the inner layers; the clipping wrapper has no filter or negative inset that could paint outside the card.

## Switch or revert

On mobile Home, open the top-right **Options** menu and choose **Use original home layout**. Choose **Use new home layout** to return. The preference persists on that browser/device and uses a session fallback when browser storage is blocked.

The original `SectionCards`, `MobileDailySessions`, charts, and `mobile-dashboard.css` remain in use for the original layout. A local source snapshot of the pre-change homepage and app shell is saved in `artifacts/mobile-home-redesign/original/`. The baseline Git revision is `1fdb72b`.

## Preview

Run `npm --prefix ui run build`, then `node tools/desktop-preview.mjs`, and open `http://127.0.0.1:5194/` at phone width. This preview uses synthetic data and does not connect to the backend, credentials, or training providers. Add `?theme=dark` for the dark appearance.

## Responsiveness release — October 19, 2026

Startup was measured before changing the implementation. The first live desktop Home check reached session verification at 2,134ms, useful cached content at 2,479ms and refreshed data at 3,720ms. An explicit 390×844 phone reload reached Home at 541ms; an earlier 663ms sample was taken around viewport setup and is excluded from the phone comparison. The consistent approximately 330ms handoff after authentication came from entering a fresh React lazy/Suspense boundary even when its module had already been downloaded.

Route preloaders now retain the resolved component and render it directly on the first commit. Desktop Home's initial card module also warms before authentication finishes. Protected training reads start alongside session verification, rather than after the page mounts. Returning sessions use a small version receipt rather than downloading the entire unchanged snapshot; a receipt for a different cached version cannot validate it. Nutrition's protected initial diary read uses the same overlap, with date matching and ordinary response validation. Every early request still passes the existing server authentication checks; anonymous responses never render private content. Startup requests are one-shot and discarded on session/cache resets. The mobile hero photo is requested early; off-screen charts and images retain their existing lazy loading.

The preserved original production build and optimized build were compared at 390×844 against identical synthetic APIs with a fixed 500ms API delay. Three original runs reached refreshed Home data at 1,498, 1,472 and 1,404ms. Three optimized runs reached it at 651, 634 and 621ms. Median refreshed readiness improved **56.9%**, from 1,472ms to 634ms. First cached content in those same runs improved from median 921ms to 589ms (36.0%). These are distinct measures; the 56.9% result is not a promise for every network, device or route. Diagnostic records and the original build are retained in ignored `artifacts/responsiveness/`.

Mobile controls now respond on pointer-down with a small scale/opacity change and a short release transition. Passive capture handlers do not delay clicks, generate extra clicks or prevent scrolling. Movement, cancellation, blur and component cleanup clear the state. Reduced-motion preferences remove scale movement. Page surfaces reveal with a short opacity transition, without transformed wrappers or artificial loading delays.

Nutrition uses the app-level toast portal above the editing screen, positioned inside the visual viewport. Adding food displays a pending toast before product lookup or saving starts, then updates the same notification on confirmation or failure. Complete search results avoid another product lookup. Quick-add preserves the search field's focus. Daily totals update provisionally before the request and roll back on failure; older reads cannot overwrite them. Synchronous locks prevent duplicate taps. Library saves use the same immediate feedback. A local delayed-save check confirmed the pending message, focused input and provisional breakfast totals; a rejected request restored the prior log. A retry confirmed one serving, with no duplicate. The toast remained within the visible 390×430 keyboard-sized viewport while editing was active.

Workout moves, deletes, descriptions, planned values, note saves and workout creation now project locally before the provider request. Provisional rows cannot be edited as provider events. Structured editor saves use the same staged projection and mark the training snapshot busy. Intervals.icu writes, independent readback verification, durable provider claims and existing draft recovery remain intact. A pending visual state is never represented as a successful provider sync. Failures roll back only their own fields, preserving unrelated edits and newly received completed activities. Session changes prevent a failed old request from restoring private data after sign-out. Known queued edits remain explicitly pending. Provider receipt at the watch remains outside the app's observable boundary.

The final local preflight passes 499 backend tests and 319 UI tests, production build, UI lint and whitespace checks. Both dependency audits report zero vulnerabilities. Added cases cover first-commit preloaded rendering, retrying a failed preload, version receipt matching and mismatch recovery, provisional creations, rollback with concurrent completion, stale duration-label replacement and rollback, optimistic nutrition totals and invalidation of pre-save reads. QA uses disposable synthetic records; no live food or workout records are changed.
